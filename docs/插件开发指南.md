## 0. 先说清楚一件事：这不是在手机上跑 Python

Home Assistant 的集成是 **Python**，鸿蒙应用跑不了，也不能运行时加载原生代码
（鸿蒙没有动态加载字节码的公开能力）。所以：

> **「兼容 HA 插件」= 提供一套协议，让第三方照着 HA 集成的逻辑，用 JavaScript 重写一份鸿蒙插件。**

好消息是：HA 集成里 90% 的工作是「HTTP 请求 + 鉴权 + JSON 解析」，这些在 JS 里几乎是逐行直译的。
真正难移植的只有两处：**私有二进制协议**和**长连接**（MQTT/WebSocket）——
这两类靠宿主提供的原始 socket 桥来做（`Host.udp` / `Host.tcp` / `Host.tls`，见 §7.4），
协议本身仍要在 JS 里自己实现。

一次典型移植的工作量：**纯 REST 云 API 约半天到一天；带局域网私有协议约一周。**

## 1. 插件是什么

一个 zip 包，里面至少有 `plugin.json` 和 `main.js`：

```
my-platform-1.0.0.zip
├── plugin.json      # 清单：名字、权限、能力声明、登录方式
├── main.js          # 插件逻辑（runtime = "js" 时）
└── icon.png         # 可选，插件卡片图标
```

宿主在**ArkWeb 的 JavaScript 沙箱**里加载 `main.js`，并通过 `Host` 对象把原生能力借给你。
你拿不到 `@ohos.*` 的任何 Kit，一切原生能力都走 `Host.*`。

### 1.1 ⚠️ 只能有一个文件 —— 不能用 `import`

宿主只读取 `plugin.json` 里 `entry` 指向的**那一个文件**，把它的内容原样包进
一个 IIFE 用 `runJavaScript` 执行（见 `PluginSandbox.wrapSource`）。所以：

- **`import` / `export` 会直接抛语法错误** —— 那不是 ES Module 环境
- 拆出去的独立 `.js`（比如 `crypto.js`）**不会被加载**，是孤儿文件
- 压缩包里多放几个文件不会报错，只是它们永远不会被执行

也就是说，**插件必须自包含**：所有辅助函数都写在这一个文件的闭包里。
几百上千行是正常的（内置的米家插件就是单文件 ≈700 行）。

如果确实想拆，只能自己做拼接：把多个源文件在构建期合并成一个 `main.js`
（比如简单的 `cat a.js b.js > main.js`），因为闭包共享作用域，
函数可以直接互相调用。但宿主侧不提供任何模块解析。

## 2. plugin.json

```jsonc
{
  "schemaVersion": 1,
  "id": "com.example.myplatform",     // 全局唯一，建议反向域名
  "name": "我的平台",                  // 显示在插件卡片上
  "version": "1.0.0",                 // semver
  "runtime": "js",                    // "js"（有代码）| "declarative"（纯 JSON，见 §9）
  "entry": "main.js",
  "hostMinVersion": "2.0.0",          // 要求的最低宿主版本
  "description": "一句话说明",
  "author": "you",
  "homepage": "https://github.com/you/repo",
  "license": "MIT",

  "permissions": ["network", "secureStore", "crypto"],   // 见 §3
  "login": { "type": "qr" },                              // qr | web | form，见 §5
  "capabilities": {                                       // 宿主据此显示/隐藏入口
    "homes": true,
    "devices": true,
    "scenes": false,
    "spec": false,
    "statistics": false,
    "messages": false,
    "consumables": false,
    "lanControl": false,
    "gatewayControl": false,
    "stream": false,                                      // 摄像头实时取流，见 §6.4
    "gatewayAdmin": false                                 // 网关局域网管理面，见 §6.5
  },
  "update": {
    "source": "github",                 // github | url
    "repo": "you/repo",                 // source=github 时
    "assetPattern": ".*\\.zip$"
  }
}
```

**`capabilities` 是给宿主的承诺**，不是可选项：声明 `false` 的能力，宿主会隐藏对应入口；
声明 `true` 却没实现，宿主调用时你会收到错误。**宁可少声明。**

## 3. 权限（`permissions`）

安装时宿主会逐条展示给用户，用户确认后插件才被注册。

| 权限 | 你能做什么 | 不给会怎样 |
| --- | --- | --- |
| `network` | 通过 `Host.http()` 发任意 HTTP(S) | 一切云 API 都不可用 |
| `secureStore` | 读写**本插件私有**的凭据区 | 无法保存 token，每次启动都要重新登录 |
| `crypto` | 调用原生 SHA1/SHA256/HMAC/随机数 | 只能用 JS 自己实现（慢且容易写错） |
| `lan` | `Host.udp` / `Host.tcp` 直连局域网设备 | 无法做局域网发现/控制 |
| `mqtt` | `Host.tls` 长连接（含客户端证书） | 无法连公网 broker |
| `log` | 写入宿主的反馈日志 | 出问题时无法排查 |

> `secureStore` 的存储是**按 pluginId 隔离**的：别的插件读不到你的 key，你也读不到别人的。
> 隔离靠的是「每个插件一份独立存储实例」，不是 key 前缀 —— 前缀能被猜到，独立实例不能。
>
> ⚠️ 桥上的**权限判定发生在每一次调用**，不是安装时一次性放行。声明了没授权
> 就等于没有；想确认自己拿到了什么，看 `plugin.permissions`（§2 的清单投影）。

## 4. 插件的生命周期

宿主加载 `main.js` 后，约定全局对象 `Plugin`：

```js
// main.js
Plugin.register({
  // ① 初始化：拿到凭据，准备好客户端。可以不联网。
  //    返回 true = 已连接可用；false = 需要登录
  async init(ctx) {
    const cred = await Host.secureStore.get('auth');
    if (!cred) return false;
    this.auth = JSON.parse(cred);
    return true;
  },

  // ② 登录（详见 §5）。未登录时插件卡片上的按钮会调到这儿。
  async loginBegin() { /* ... */ },
  async loginPoll(sessionId) { /* ... */ },
  async loginSubmit(sessionId, fields) { /* ... */ },
  async loginCancel(sessionId) { /* ... */ },

  // ③ 数据面。方法名与 §6 的表一一对应。
  async getHomes() { /* ... */ },
  async getDevices(homeIds) { /* ... */ },

  // ④ 销毁：断开长连接、停掉定时器。宿主禁用/卸载插件时调用。
  async dispose() { /* ... */ }
});
```

`ctx` 里带：`pluginId`、`dataDir`（本插件的私有沙箱目录）、`hostVersion`、`locale`。

### 4.1 你的代码跑在哪里 —— 一个会影响「插件什么时候能连上」的约束

插件运行在 ArkWeb 的 JS 沙箱里，而这个沙箱的**宿主是一个页面里的 `Web` 组件**
（零尺寸、不可见）。这意味着：**只有挂了那个组件的页面活着，插件才可能被加载。**

宿主为此抽了一个 `PluginSandboxHost` 组件，挂在**任何需要用到插件的页面**上
（目前是「数据源与插件」页和首页）。如果你在真机上遇到「插件明明装了、启用了，
却一直显示未连接」，先确认当前这页是不是挂着沙箱宿主 —— 这曾经是一个真实的自锁 bug：

> 冷启动路由发现「有已启用的插件」→ 直接进首页（跳过插件页）→ 插件页从未加载
> → 沙箱从未 attach → `connect()` 一律失败 → 插件永远显示「未连接」→
> 而首页当时又没有回插件页的入口，用户被困住。
>
> 根因是**路由的判断（「有插件就能用」）和沙箱的宿主位置（只在插件页）互相矛盾**。

🔴 **那个宿主 `Web` 的尺寸不能是 0。** 零尺寸组件不参与布局测量，ArkUI 就不会为它
创建 nweb 实例，`onPageEnd` 永不触发 —— 于是组件在树里"挂着"、却根本没跑起来。
真机日志里的特征是这样一组三行：

```
[PluginSandbox] 沙箱未就绪，无法加载插件
NativeArkWeb BindWebTagToWebInstance webTag:arkweb:1
fail to find a valid nweb with id:-1 Tag:arkweb:1
```

**`id:-1`** 就是判定依据：controller 从未绑定到任何 nweb 实例。
所以宿主用的是 **1vp**（肉眼不可见，但足以进入布局）+ `Visibility.Hidden`。

⚠️ 注意区分两种 `id:-1`（别被吓到）：

- **零尺寸那种**：`id:-1` 之后**永远等不到** `CreateNWeb`，沙箱彻底没起来；
- **冷启动那种**：`JsConstructor`（controller 构造）先于 nweb 创建跑了一次绑定、扑空一次，
  紧接着 `CreateNWeb NWebId: 1, size 1*1` 就出来了 —— **一次性的、无害的**，见 §4.1.7。

判定只看一条：**后面有没有跟 `CreateNWeb`。**

如果你在日志里遇到「沙箱未就绪」，先搜有没有 **「沙箱宿主页面就绪」** 这一行：

- **有** → 沙箱本身没问题，去查插件侧（用 §13.1 的模拟器）。
- **没有** → 承载沙箱的组件没跑起来，与插件无关。按顺序查：
  ① 当前页面挂了 `PluginSandboxHost` 吗；
  ② 它的 `Web` 尺寸是不是被改成了 0（或被某个 `if` 条件包住没渲染）；
  ③ 有没有 `fail to find a valid nweb` 之类的 ArkWeb 报错。

对插件作者的影响：`init()` 可能比你以为的晚得多才被调用，而且**页面切换时会重来**。

### 4.1.1 `runJavaScript` 的返回值会「多一层引号」

这是排查插件问题时最容易误判的一类现象，单独说清楚。

ArkWeb 的 `controller.runJavaScript(script)` 声明返回 `Promise<string>`，
但**字符串结果在部分内核/版本上会被再包一层引号**：

| JS 表达式返回 | 宿主可能收到 |
| --- | --- |
| `'yes'` | `yes`（旧内核）或 `"yes"`（实测内核） |
| `'ok'` | `ok` 或 `"ok"` |
| `JSON.stringify({a:1})` | `{"a":1}` 或 `"{\"a\":1}"` |

第三行是真正的杀手：宿主本该 `JSON.parse` 出一个对象，
剥壳缺失时 parse 出来的**是字符串**，于是 `obj.ok` 恒为 `undefined`，
所有插件方法调用一律失败 —— 而插件侧日志完全正常，
看上去像是「宿主的调用根本没发出去」。

宿主现在的做法是：**凡是比较 `runJavaScript` 的返回值，先过
`PluginSandbox.normalizeJsResult()`**（去空白 → 剥一层引号 → 再去空白），
用于三处：bootstrap 的 `fatal:` 前缀判断、`loadPlugin` 的注册探针、
`unwrapResult` 的调用结果解析。

所以你在真机日志里看到这类内容，**先怀疑包装，不要怀疑插件**：

```
[PluginSandbox] 插件 xxx 未成功注册: "yes"
```

值里带引号 = 包装没剥干净。与之相对，真正的失败长这样：

```
[PluginSandbox] 插件 xxx 未成功注册: no:插件注册时抛的原因
```

所以：

- 不要在模块顶层做「只做一次」的初始化，把它放 `init()`；
- socket 回调必须在 `init()` 里重新注册（页面重建后回调注册表会清空，见 §7.4）；
- 不要把状态放在模块级变量里指望它跨页面存活 —— 虽然单例插件实例确实会存活，
  但页面重建后 `init()` 会再跑一次，别让重复初始化产生副作用（比如重复开 socket）。

### 4.1.2 宿主桥要跨**两轮页面加载**才可用

这一条影响你对「`init()` 什么时候能调通 Host」的预期，值得单独知道。

SDK 对 `registerJavaScriptProxy` 的说明里有一句关键的：

> Registed objects will not appear in JavaScript until the page is next (re)load.

也就是说**注册当次在 JS 里是看不到的**。宿主为此走了两轮：

```
第 1 轮 onPageEnd   页面刚起来
   ├─ 装配 controller / bridge
   ├─ registerJavaScriptProxy(...)
   └─ 主动重载页面（loadUrl）
      ✗ 此时不能跑 bootstrap —— window.Host 还不存在

第 2 轮 onPageEnd   重载完成后，代理才真正出现在 JS 上下文
   └─ bootstrap：把扁平代理缝成 Host.secureStore.get 这样的命名空间
      └─ 成功后才 autoConnectAll()（才开始加载插件）
```

**对你的影响**：从「页面开始加载」到「`init()` 能被调用」中间隔了**两次页面加载**，
比你直觉上要久。所以：

- 不要假设「进页面之后马上就能连上」；
- 如果 `init()` 里第一次调 `Host.http` 就报 `undefined`，先怀疑桥还没到第 2 轮，
  而不是插件写错了。日志里搜 **`[PluginSandbox] 宿主桥就绪`** —— 出现它才代表能用。

宿主曾把这里写成「注册完就地 bootstrap」，真机日志给出的就是：
`bootstrap 失败: fatal:原生桥未注册`，插件因此永远拿不到宿主能力。

### 4.1.3 沙箱会被 ArkUI 重建 —— 弹窗也会触发

**对你的影响**：如果一次插件调用横跨了沙箱重建，那次调用就会莫名失败。

真机上抓到的完整因果链（打开登录面板那一刻）：

```
OnInvokeMethodAsync: async method name: crypto_randomBytes   ← 插件在调桥，一切正常
bindsheet lifecycle change to onWillAppear state             ← 登录半模态弹出
ForEachNode skip mark dirty                                  ← 页面组件树重排
JsConstructor: NapiWebviewController::JsConstructor start    ← controller 被重建！
BindWebTagToWebInstance webTag:arkweb:2                      ← nweb 从 1 换成 2
native proxy object not found, name:Host                     ← 旧代理丢了
```

也就是说——**仅仅是把半模态弹出来，就足以把承载沙箱的 Web 重建掉**。
这解释了那个看着莫名其妙的 `cannot read property ok of null`：
调用进行到一半，对面的桥没了，返回值跨过来变成 `null`。

宿主的应对（都是为了让重建**不再打断正在进行的调用**）：

- `WebviewController` 改为**模块级单例**（原来写作组件字段，每次重建就新造一个，
  连带新 nweb、旧代理失效）。组件会被重建是 ArkUI 的正常行为，拦不住；
  但 controller 必须跨重建存活。
- `aboutToDisappear` **不再注销代理、不再 detach** —— 组件重建比想象中频繁，
  每次重建都跑一遍会把**正在被使用**的代理注销掉。沙箱生命周期改由
  `pluginSandbox` 自己掌握（只在退出登录 / 卸载 / 应用退出时释放）。
- `attach()` 只在 **controller 真的换了**时才重置桥状态；
  `registerProxy()` 幂等（重复注册会叠加计数，且注册瞬间代理不可用）。

**对插件作者的建议**：把每次调用都当成「可能中断」来写。
长流程（比如扫码登录的多步请求）不要依赖跨调用的桥状态，
该存的状态存在插件自己的闭包里。

### 4.1.4 `runJavaScript` **不等 Promise 结算** —— 所以调用结果是「回推」回来的

这一节解释一个**你看不到但必须理解**的机制。不理解它，
排查真机问题时会把宿主的机制问题误判成自己的插件写错了。

**SDK 原文**（`@ohos.web.webview.d.ts:3363-3372`）：

> If you cannot obtain the return value by executing the asynchronous method,
> you need to determine whether to use synchronous or asynchronous mode based
> on the specific situation.
>
> **If the JavaScript script fails to execute or has no return value, null will be returned.**

也就是说：`runJavaScript(script)` **不会等 `script` 里的 Promise 结算**。
你的插件方法几乎是清一色的 `async`，宿主当然没法「等它返回」。

历史教训：宿主早期把调用脚本写成

```js
(async function () {
  var result = await fn.apply(impl, argv);
  return JSON.stringify({ ok: true, data: result });
})();
```

顶层交出去的是一个 **Promise 对象**，引擎判定「脚本没有返回值」，
宿主拿到的是字符串 `"null"`，于是**每一次插件方法调用都报**：

```
插件方法 getDevices 返回的不是有效信封: null
```

而插件侧日志一切正常 —— 这种「宿主报错、插件无辜」的组合最耗排查时间。
（同理，`bootstrap` 之所以一直能通，是因为它写的是**同步** `return 'ok'`。）

**现在的机制**（你不需要写任何代码，但要知道它怎么工作）：

```
宿主                                  插件沙箱
 │
 ├─ runJavaScript(派发脚本) ──────────►  ① 同步执行：
 │                                       window.__miha_invoke__(callId, method, args)
 │                                       ├─ 把 plugin[method] 丢进一个**不 await** 的 IIFE
 │                                       └─ 立刻同步 return 'accepted'
 │  ◄──── 'accepted'（宿主确知已受理）
 │
 │   （宿主在派发**之前**就挂好了等待槽）
 │
 │                                      ② 你的 async 方法自己结算
 │                                      ③ 经桥回推：Host.__flat.invoke_settle(callId, 信封)
 │  ◄───────────────────────────────────
 └─ 拆信封 → 返回 / 抛错
```

三个由此而来的**行为约定**：

| 现象 | 含义 | 你该做什么 |
| --- | --- | --- |
| 报「插件运行环境正在重建，请重试」 | 沙箱页面被 ArkUI 重建（见 §4.1.3），派发函数还没重新注入 | 重试即可；宿主会顺手补注入。别怀疑自己的代码 |
| 报「插件方法 X 未受理（脚本返回 …）」 | 派发脚本没跑起来 —— 语法错或沙箱状态异常 | 检查插件 `entry` 文件是否有语法错误 |
| 报「插件方法 X 调用超时」（60s） | 你的方法真的没有结算 —— 某个 `await` 永远没 resolve | 检查网络请求是否漏了超时、回调是否漏了 resolve |

**⚠️ 不要试图绕过它**：SDK 里**没有**可用的替代通道。
`runJavaScriptExt` 返回的 `JsMessageExt` 同样没有任何 Promise 支持声明；
而 `setWebMessagePorts` / Web 组件的 `onMessage` 在**本 SDK 中不存在**
（`WebAttribute` 的全部 165 个方法里没有 message/port 相关项），
所以 H5 的 `window.onmessage` 消息端口方案用不了。

**顺带一个推论**：你的插件方法是**位置参数**接收的。
`__miha_invoke__` 里写的是 `fn.apply(impl, args)`，
所以 `Host` 调用 `invoke('setProperty', [did, siid, piid, v])` 时，
你的 `async setProperty(did, siid, piid, v)` 就能直接拿到四个参数。
（如果宿主改成传数组，这里会变成一个数组参数，注意别踩。）

### 4.1.5 代理对象会被 GC —— 宿主必须自己攥住它

**真机日志**（运行一段时间后突然出现，与前面几条的「一启动就坏」不同）：

```
OnInvokeMethodAsync: async method name: invoke_settle        ← 插件在回推结果，机制本身正常
host does not have the interface method, 2, default value    ← 但宿主对象上已经查不到这个方法
FindObject: WebviewJavaScriptResultCallBack::FindObject Unknown object: objectId = 1073741825
OnObjectWrapperDeleted ...
native proxy object not found, name:Host
```

**根因**：宿主交给 `registerJavaScriptProxy` 的那个代理对象，
早期写成 `registerProxy()` 里的**局部变量** —— 方法一返回就没人引用了。
ArkWeb 内部只持有一个 wrapper（日志里的 `objectId`），
底层 ArkTS 对象被 GC 后 wrapper 就悬空，`FindObject` 自然找不到。

**这类故障的特征是「延迟出现」**：刚启动时一切正常（对象还没被回收），
跑一阵子才开始报错，且**与用户操作无关**。排查时很容易误判成插件的问题。

宿主的修法（两层）：

| 层 | 做法 | 解决什么 |
| --- | --- | --- |
| 保活 | 用字段 `proxyObject` 强引用住那个代理对象 | 从根上防止 wrapper 悬空 |
| 兜底 | 回推失败时结果留在**孤儿表**（`window.__miha_orphan__`），宿主超时前捞一次 | 万一还是断了，不让用户白等 60 秒 |

**对你（插件作者）的影响**：没有直接影响 —— 这些都是宿主内部的事。
但如果你在日志里看到 `FindObject Unknown object` 或
`host does not have the interface method`，**那不是你插件的 bug**，
是宿主的保活出了问题，报给宿主维护者即可。

### 4.1.6 `@Watch` 会**同步重入** —— 别在「清标记」和「推路由」之间踩它

这条听着和插件无关，实际是**「插件已启用但首页连不上」的另一条死路**，所以放在这里。

宿主有一条冷启动通路：通知里的设备 did 写进 `AppStorage`，
首页起来后消费它、直接跳到设备详情页。真机日志里**每次冷启动**都留一条：

```
FIX THIS APPLICATION ERROR: @Component 'HomePage':
  State variable 'pageInfos' has changed during render!
  It's illegal to change @Component state while build
  (initial render or re-render) is on-going. Application error!
navigation necessary to immediately trigger a refresh
```

**为什么这条会牵连插件**：首页跳详情 → 详情页先渲染 → 插件设备列表
还没从沙箱回推 → 详情页拿不到属性 → 用户退回首页，看到的还是「未连接」。
链路本身没错，只是**跳得太早**了。

#### ⚠️ 这里有个反直觉的地方：只推后调用**治不了根**

第一版修法是把 `aboutToAppear` 里的调用推后一个消息循环：

```ts
setTimeout((): void => { if (this.pageAlive) { this.consumePendingDeviceDetail(); } }, 0);
```

**实测无效**（下一份真机日志仍在报同一行）。原因是重入**发生在函数内部**，
不在调用时机上。

#### 真正的根因：`@StorageProp` + `@Watch` 是同步回调

消费函数长这样，看着完全正常：

```ts
private consumePendingDeviceDetail(): void {
  const did = this.pendingDeviceDetailDid;          // 先从 @StorageProp 读一份快照
  if (did === undefined || did.length === 0) { return; }
  AppStorage.setOrCreate('pendingDeviceDetailDid', '');   // ← ① 清标记
  ...
  this.pageInfos.pushPathByName('deviceDetail', ...);     // ← ② 推路由
}
```

而 `pendingDeviceDetailDid` 声明为：

```ts
@StorageProp('pendingDeviceDetailDid')
@Watch('onPendingDeviceDidChanged')      // ← onPendingDeviceDidChanged 又调回本函数
pendingDeviceDetailDid: string = '';
```

于是 ① 那行会**同步**触发 `@Watch` → 第二次进入本函数：

```
第 1 次进入 → ① setOrCreate('') → @Watch 同步重入 → 第 2 次进入
   第 2 次拿到的 did 仍是非空（方法栈上的局部变量还没失效）
   → 跳过 ① → 直接走到 ② `pushPathByName`   ← 💥 推路由落在重入里
```

而重入是从 `aboutToAppear`（首帧 build 之前）发起的 —— 所以这次 push
落在渲染期内。**`setTimeout` 包在外层没用，因为重入是函数自己触发自己的。**

#### 修法：把「推路由」移到**最后一步**，并让重入变成 no-op

```ts
private consumePendingDeviceDetail(): void {
  const did = this.pendingDeviceDetailDid;
  if (did === undefined || did.length === 0) { return; }
  // ① 先清标记。重入会在这里发生，但此时还没碰路由，安全。
  AppStorage.setOrCreate('pendingDeviceDetailDid', '');
  const target = this.findDeviceByDid(this.allVisibleDevices, did);
  if (target !== null && this.isRouterDevice(target)) {
    this.showRouterWarningDialog(did);
    return;
  }
  // ② 路由放最后一步，且在消息循环里补一次 —— 让本轮状态写入先结算干净。
  setTimeout((): void => {
    if (this.pageAlive) {
      this.pageInfos.pushPathByName('deviceDetail', new DeviceDetailRouteParam(did));
    }
  }, 0);
}
```

两个要点：

1. **重入进来的那次因为 `did` 已空会立刻 return** —— 全程只有一次 push；
2. 那次 push 发生在所有状态写入**之后**，不再有「边改边渲染」。

#### 通用规则（可推广）

- **`@Watch` 是同步的。** 在 `@Watch` 回调用链上改被观察的值，等于手动制造递归。
  要么把值变更做成幂等（像上面那样让重入 no-op），要么改完值再处理副作用。
- **一个函数里同时有「改状态」和「产生副作用」时，顺序就是语义。**
  先把所有状态写完，最后再跳页 / 弹窗 / 发请求。
- **判据**：看到 `State variable 'X' has changed during render!`，
  不要只盯着调用它的位置 —— 去 `X` 的 `@Watch` 链路上找**同步重入**。
- ⚠️ 同文件里 `openDeviceFromSheet` 用的是同款「锁变量 + setTimeout」写法，
  但它那个锁**没有挂 `@Watch`**，所以不需要改。**动这类代码前先确认锁变量有没有挂 `@Watch`** ——
  有 `@Watch` 和没有 `@Watch` 的锁，语义完全不同。

### 4.1.7 `web controller is nullptr` 是 ArkWeb 内部噪音

日志里可能见到：

```
web controller is nullptr
```

它在冷启动、`Web` 组件**首次构建**时出现 —— 此时 `WebviewController`
的 native 侧还没绑定完，ArkWeb 内部抢先访问了一次。**宿主无感**：
紧接着就能看到 `CreateNWeb NWebId: 1, size 1*1` 与
`NWeb size change from 0*0 to 1*1`，说明 nweb 正常建起来了。

**判定方法**：看这三行是否**配对出现**。
只要 `size 1*1` 在，沙箱就是好的；如果**只有** `web controller is nullptr`
而没有任何 `CreateNWeb`，那才是真的没起来（回去看 §4.1 的尺寸问题）。

#### 顺带：`arkweb:N` 的编号别拿来当「第几个实例」数

冷启动日志里会先看到一组看似矛盾的行：

```
NativeArkWeb BindWebTagToWebInstance webTag:arkweb:0
fail to find a valid nweb with id:-1 Tag:arkweb:0
...
CreateNWeb NWebId: 1, size 1*1
```

`fail to find a valid nweb with id:-1` **在冷启动出现一次是正常的**：
controller 构造（`JsConstructor`）先于 nweb 创建，绑定动作跑了一次扑空，
等 `CreateNWeb` 出来后自然接上 —— 与 §4.1 说的「零尺寸导致**永远** `id:-1`」
是两回事（那条的特征是 `id:-1` 之后**永远没有** `CreateNWeb`）。

另外 `webTag:arkweb:0` 的尾号是 **ArkWeb 进程内所有 Web 实例的轮转计数**，
不是「本应用的第几个沙箱」—— 别拿它推断实例数量，也没有「必须从 1 开始」的约定。

### 4.1.8 沙箱重建后会自动自愈

沙箱的 Web 页面被 ArkUI 重建后（见 §4.1.3），JS 上下文整个换新 ——
`window.Host`、`__miha_invoke__`、以及你注册的 `impl` 全都没了。
宿主会在检测到这一情况时**自动重装**：重注册代理 → 重载页面 →
补 bootstrap → 重注你的插件源码。

因此：

- **你的插件会被重新 `register` 一次**。如果 `init()` 里有副作用
  （写文件、建连接、改全局状态），要么做成幂等，要么在 `dispose()` 里收干净。
- 重建**期间**的调用会失败并提示「插件运行环境正在重建，请重试」。
  这通常只持续几百毫秒，重试即可。
- 自愈只在**同一插件**范围内进行 —— 如果插件已被禁用（`disposeCurrent`），
  自愈不会把它装回来。所以不用担心「停用了却还在跑」。

## 5. 登录（重点）

登录是**有状态会话**，不是纯函数。原因很实在：很多平台的二维码流程里，
「生成二维码」和「轮询结果」两步必须共用同一组随机参数（设备 ID、cookie、UA），
拆成两个无状态请求就直接失败。米家扫码就是典型：`deviceId` / `passO` / cookie 串必须在一次流程内保持连贯。

### 5.1 协议

```
宿主 → 插件                             插件 → 宿主
{ op: "login.begin" }                 → { sessionId, view }
{ op: "login.poll",   sessionId }     → { state, ... }
{ op: "login.submit", sessionId, fields } → { state, ... }
{ op: "login.cancel", sessionId }     → { state: "cancelled" }
```

`state` 取值：`pending` / `success` / `expired` / `error` / `cancelled`。

### 5.2 三种登录视图（宿主原生渲染，你只给数据）

#### `qr` —— 扫码（米家扫码、大部分国内厂商）

```js
async loginBegin() {
  const s = newSession();                       // 你自己的会话对象
  const ticket = await buildQrTicket(s);        // 调平台接口
  sessions.set(s.id, s);
  return {
    sessionId: s.id,
    view: {
      type: 'qr',
      imageUrl: ticket.qrUrl,      // 或 imageDataUri（base64 png）
      hint: '请用平台 App 扫码',    // 宿主显示在二维码下方
      expiresIn: 180,              // 秒，宿主倒计时并提示刷新
      pollInterval: 1000           // 毫秒
    }
  };
}

async loginPoll(sessionId) {
  const s = sessions.get(sessionId);
  const r = await pollOnce(s);
  if (r.pending) return { state: 'pending' };
  await Host.secureStore.set('auth', JSON.stringify(r.credential));
  return { state: 'success' };
}
```

> **为什么 `imageUrl` 要宿主去下载？** 因为沙箱里的 JS `fetch` 受 CORS 限制，
> 而二维码接口通常不带跨域头。宿主会用自己的网络栈把图片取回来。
> 如果接口本身就带 CORS 头，你可以直接给 `imageDataUri`。

**三个会静默出错的细节**（对照 `PluginManager.beginLogin` / `startPolling`）：

1. **`pollInterval` 必须 > 0**。宿主只在 `pollInterval > 0` 时才起轮询。
   省略或写 0 = **完全不轮询**，二维码挂在那儿永远不会被处理，
   用户扫了也没反应，而且没有任何报错。

2. **`loginPoll` 只会收到 `sessionId`**，没有第二个参数。
   轮询地址（米家的 `lp`）、会话对象这些必须存在**插件自己的状态里**
   —— 宿主不替你保存、也不会回传。详见上面的 `sessions.get(sessionId)`。

3. **「还没扫」要返回 `state: 'pending'`，不要抛错**。
   宿主对连续异常是零容忍的：**连续 3 次失败就判登录失败并关掉弹窗**
   （`startPolling` 里的 `consecutiveErrors >= 3`）。长轮询超时、
   网络抖动都属于正常情况，一律按 `pending` 返回。真正该报错的是
   「二维码过期」→ `expired`，或凭据不合法 → `error`。

#### `web` —— OAuth 授权码（HA 官方 OAuth、Tuya、SmartThings）

```js
async loginBegin() {
  return {
    sessionId: s.id,
    view: {
      type: 'web',
      url: 'https://.../oauth/authorize?client_id=...&redirect_uri=...',
      stopPrefixes: ['myapp://oauth/callback']   // 宿主拦到这个前缀就交回给你
    }
  };
}

async loginSubmit(sessionId, fields) {
  // fields.callbackUrl 就是宿主截到的完整回调 URL
  const code = new URL(fields.callbackUrl).searchParams.get('code');
  const token = await exchangeToken(code);
  await Host.secureStore.set('auth', JSON.stringify(token));
  return { state: 'success' };
}
```

#### `form` —— 表单（自建网关、需要账密的平台）

```js
view: {
  type: 'form',
  fields: [
    { key: 'host',     label: '服务器地址', type: 'text',   placeholder: 'http://192.168.1.10:8123' },
    { key: 'token',    label: '长期访问令牌', type: 'password' },
    { key: 'remember', label: '记住', type: 'switch', default: true }
  ],
  submitLabel: '连接'
}
```

宿主按 `fields` 渲染原生输入框（不是网页），用户点提交后调 `loginSubmit(sessionId, { host, token })`。

### 5.3 登录成功之后

**你自己保存凭据**（`Host.secureStore.set`），宿主不碰、也看不见内容。
宿主只知道你的 `state === 'success'`，然后把卡片状态翻成「已连接」。

刷新令牌（refresh token）也由你自己管：宿主在每次调用数据面方法前会调 `init()`，
你可以在 `init()` 里判断过期并静默刷新。

### 5.4 登录界面由宿主渲染（现在的状态）

登录 UI **已经接线**：插件只要在 `plugin.json` 里声明 `login.type`，
插件卡片上就会出现「登录」按钮，点开后由宿主按你给的视图数据渲染原生界面。

分工是这样的：

| 谁 | 负责什么 |
| --- | --- |
| **你（插件）** | 在 `loginBegin` 里返回**视图数据**（二维码图片地址 / 授权页 URL / 字段描述），并实现 `loginPoll` / `loginSubmit` / `loginCancel` |
| **宿主** | 画界面、起轮询定时器、跑倒计时、开 Web 视图、拦回调 URL、收表单值 |
| **你自己** | 凭据存取（`Host.secureStore`），宿主不碰也看不见 |

几个必须知道的约定：

- **二维码图片由宿主下载**。你不能在沙箱里 `fetch` 图片（CORS 挡着），
  所以 `imageUrl` 直接给 http(s) 地址或 `data:` URI，宿主负责加载。
- **`pollInterval` 是宿主轮询你的间隔**（毫秒）。`qr` 视图必须给，
  否则宿主不会主动来问（它不会去猜节奏）。`form` / `web` 不用给。
- **`expiresIn` 可选但建议给**。宿主会跑一个倒计时，归零就把状态判成 `expired`。
  不给的话用户可以对着一个早就失效的二维码看很久。
- **`web` 视图的回调**：宿主在导航到以 `stopPrefixes` 任一元素**开头**的地址时
  拦下这次跳转，把完整 URL 作为 `fields.callbackUrl` 交给你（`loginSubmit`）。
  这是前缀匹配不是全等 —— 授权回调通常带一长串 query。
- **`form` 的字段类型**：`text` / `password` / `switch`。`switch` 的值按
  `'true'` / `'false'` **字符串**传递（协议里所有表单值都是字符串）。
  未知类型会被当成 `text`，不会报错。

**没有登录需求的插件就不要写 `login` 字段** —— 那会让卡片上出现一个
「登录」按钮，点开是个空表单。缺省即表示「本插件不需要凭据」。

> ⚠️ 整套登录流程与宿主界面**尚未经过真机验证**，只在编译期确认过。
> 行为不符合预期时请对照 §13 的自测路径排查。

## 6. 数据面接口

一律**异步**。返回值是 JSON 可序列化的普通对象/数组（跨 JS 边界只能是 JSON）。

| 方法 | 签名 | 说明 |
| --- | --- | --- |
| `getHomes()` | `() → Home[]` | 家庭/房间分组的顶层容器 |
| `getDevices(homeIds?)` | `(string[]?) → Record<did, Device>` | **key 必须是 did** |
| `getScenes(homeId)` | `(string) → Scene[]` | 云端场景/自动化 |
| `runScene(sceneId, homeId)` | `(string, string) → Result` | 触发场景 |
| `getSpecForDevice(device)` | `(Device) → MIoTSpec \| null` | 设备能力描述，见 §6.2 |
| `createTransports(device)` | `(Device) → TransportHandle[]` | 控制通道，见 §6.3 |
| `getStatistics(did, key, type, limit, from, to)` | → `Object[]` | 历史数据 |
| `checkMessages(beginAt?)` / `getMessageList(homeId)` | → `MessageItem[]` | 通知消息 |
| `getConsumableItems(homeId)` | → `ConsumableItem[]` | 耗材（滤芯、电量等） |
| `getStreamUrl(device)` | `(Device) → {url, kind, expiresIn, source}` | 摄像头取流，见 §6.4，需 `stream` |
| `saveStreamUrl(device, url)` / `clearStreamUrl(device)` | `(Device, string?)` | 手动直播地址的存/清，见 §6.4，需 `stream` |
| `gatewayInfo / gatewayLogin / gatewayForget / gatewayClients / gatewaySetBlocked / gatewayReboot` | 见 §6.5 | 网关局域网管理，需 `gatewayAdmin` |

### 6.1 `Device` 的形状（必须与宿主一致）

**⚠️ 字段名用的是「米家原始命名」，不是驼峰。** 宿主直接跑
`HomeModels.parseDevice`，逐字段读的就是下面这些键。写成 `homeId` / `online` /
`localIp` 这类驼峰名**不会报错**，只会静默变成空字符串 ——
界面上表现为「设备没有房间、显示离线、图标不对」，极难定位。

```ts
{
  did: string,          // 平台内唯一 ID（必需，同上）
  name: string,         // 显示名
  model: string,        // 型号，宿主据此猜图标
  spec_type: string,    // → urn：能力描述标识
  room_id: string,      // → roomId
  room_name: string,    // → roomName
  home_id: string,      // → homeId
  home_name: string,    // → homeName
  isOnline: boolean,    // → online（注意是这个拼法，不是 online）
  token: string,        // 局域网控制密钥
  local_ip: string,     // → localIp
  parent_id: string,    // → parentId（子设备填网关 did）
  uid: string, pid: string, icon: string,
  group_id: string, ssid: string, bssid: string,
  orderTime: number, rssi: number,
  extra: { fw_version: string }        // → fwVersion
}
```

**这不是巧合，是刻意的**：宿主把 `parseDevice` 设计成接米家原字段，
就是为了让插件能把**云端返回的设备对象原样透传**，两边不用各维护一套映射
（映射表是 bug 温床，改一边忘一边）。所以如果你的平台就是米家体系，
`getDevices` 直接把云端对象递过去即可。

非米家的平台要自己往这个形状上凑。缺字段不要紧 —— 缺的只会是空值，
但**名字写错就是静默失效**。

同理，`Home` / `Room` 的形状：

```ts
Home: { id, name, uid, dids: string[], roomlist: Room[],
        city_id, longitude, latitude, address }
Room: { id, name, dids: string[] }
```

### 6.2 设备能力（`getSpecForDevice`）

宿主内置解析器（`siid/piid` 属性与动作模型）。

如果是比如 HA 的 entity 模型，两条路：

1. **翻译**（推荐）：把 entity 映射成 `siid=1` 下的若干 `piid`，宿主 UI 直接复用。
2. **返回 `null`**：宿主降级为「开关 + 详情」的简化卡片，你把开关的读写接到
   `createTransports()` 上。功能少，但一天就能做完。

### 6.3 控制通道（`createTransports`）

```js
async createTransports(device) {
  return [
    { id: 'cloud', kind: 'cloud', priority: 100 },   // priority 小的先试
    { id: 'lan',   kind: 'lan',   priority: 10  }
  ];
}

// 宿主随后按顺序调用：
//   getProperties(device, [{siid, piid}]) → [{siid, piid, value}]
//   setProperty(device, siid, piid, value)
//   callAction(device, siid, aiid, inList)
```

⚠️ **宿主对写操作的规则**：写操作**只在第一条可用通道上执行一次，失败不重试**。
因为局域网超时往往只是回包丢了、设备其实已经执行了 —— 再往云端重发一次就是重复开灯。
**所以 `priority` 的顺序是你的责任**：把最快、最可靠的那条通道放最前。

**可选钩子 `isTransportAvailable(transportId, device?)`**：每条通道在发起调用前，
宿主会问它一次「现在可用吗」。你不实现就按「可用」处理，让真正的调用去失败 ——
这样设计是因为反过来（默认不可用）会让没实现它的插件彻底点不动设备，
而那种失败在日志里只剩一句「跳过传输通道 xxx」，极难归因。想省一次注定失败的
外呼（比如局域网通道发现设备不在线）再实现它。

### 6.4 摄像头取流（`stream` 能力，⭐ 新增）

声明 `"capabilities": { "stream": true }` 后，摄像头设备的详情页会显示直播入口。
协议层是三条钩子，只有第一条必需：

```js
// 返回一条当前可播的地址。
async getStreamUrl(device) {
  return {
    url: 'https://.../index.m3u8',   // 必需；空串宿主会当错误处理
    kind: 'hls',                     // hls | rtsp | unknown（缺省按 hls）
    expiresIn: 600,                  // 地址预计有效期（秒）；0 = 未知
    source: 'cloud'                  // cloud = 云端短时效地址；manual = 用户手填
  };
},

// 用户在播放页手动填了局域网地址（比如 RTSP）。存不存、存哪、
// 下次 getStreamUrl 要不要优先用它，完全由你决定 —— 宿主只转发。
async saveStreamUrl(device, url) {
  this.manualUrl[device.did] = url;
  delete this.streamCache[device.did];   // 🔴 记得作废云端地址缓存，否则改了也不生效
},

// 用户删掉了手动地址，回到自动取流。
async clearStreamUrl(device) {
  delete this.manualUrl[device.did];
}
```

几个字段为什么是这么设计的：

- **`expiresIn` 别瞎编**。播放页靠它决定「还有多久该主动刷新地址」。
  短时效流地址普遍几分钟到半小时就失效，你从设备属性里读得到
  `expiration-time` 之类的字段就透传，读不到才给 0（页面按固定节拍保守刷新）。
  硬编码一个大数字必然在某个机型上黑屏。
- **`source` 是给话术用的**。手动地址播不动时该提示「检查地址和设备」，
  云端地址过期才提示「正在重取」——对着一条永不失效的手动地址反复重取，
  用户只会看到无限转圈。缺省按 `cloud` 算（老版本插件不回这个字段）。
- **取不到流是常态，不是 bug**。实测量产摄像头里只有少数机型暴露
  可直连的 HLS 流，大量机型只有私有 P2P 协议或干脆没有云播服务。
  你的 `getStreamUrl` 对没能力的机型**抛错就是正确行为**，宿主会向用户
  分档解释；千万不要返回一个凑数的地址，那只会换来播不动后的无限转圈。

### 6.5 网关局域网管理面（`gatewayAdmin` 能力，⭐ 新增）

`gatewayControl` 管的是「网关下的子设备怎么控制」；`gatewayAdmin` 管的是
「网关（路由器）本身」—— 状态看板、终端列表、拉黑、重启。声明后，
路由器类设备的详情页会出现管理入口。宿主把六个钩子包成一个**无状态**
的管理面对象，会话（stok 之类）由你在插件内部持有，页面每次进来重建
管理面也不会丢登录态：

```js
async gatewayInfo(device) {
  // → { model, firmware, routerDid, bound, loggedIn, onlineClients,
  //     uptimeSeconds, cpuPercent, memoryPercent, temperature,
  //     downloadSpeed, uploadSpeed }      读不到的数值给 -1，不要给 null
},
async gatewayLogin(device, password) { /* 拿会话凭据，存插件私有区 */ },
async gatewayForget(device) { /* 清掉保存的网关密码 */ },
async gatewayClients(device) {
  // → [{ mac, ip, name, online, blocked, downloadSpeed, uploadSpeed, onlineSeconds }]
  // 🔴 blocked 在各家固件里原始字段不一致，必须归一化成布尔再返回
},
async gatewaySetBlocked(device, mac, blocked) { /* 拉黑 / 解除拉黑 */ },
async gatewayReboot(device) { /* 重启网关 */ }
```

形状错误的代价是**静默空白**：数值字段必须是数字（读不到给 -1），
`blocked` 必须是布尔。宿主用 `routerDid` 把管理面和设备列表里的路由器
对齐，拿不到给空串的话，用户就看不出「正在管哪一台」。

## 7. Host 桥（你能调用的原生能力）

```ts
// 网络
Host.http(method, url, headers, body)    → Promise<{ status, body, headers, cookies }>   // 需 network
Host.httpForm(url, headers, fields)      → Promise<{ status, body, headers, cookies }>   // 需 network
// 🔴 fields 必须是**键值对象** `{ key1: v1, key2: v2 }`，桥负责编码成表单体。
//    不要传编好的表单字符串 —— 字符串会被桥按「字符下标」拆成
//    `0=d&1=a&2=t...` 乱码（v1.0.7 前米家插件的 401 血案根源）。
//    （桥也兼容字符串：原样作为请求体，不再编码，但请勿依赖。）

// 私有存储（按插件隔离，别的插件读不到你的 key）
Host.secureStore.get(key) / set(key, value) / delete(key)              // 需 secureStore

// ⚠️ secureStore 的读写形状陷阱（真机踩过）：
// set(key, value) 的 value 必须是字符串；但 get(key) 读回来时，
// 如果当初存的字符串以 { 或 [ 开头，Host 桥的拆包层会把它 **parse 成对象**
// 返回。所以「存 JSON 再读」拿到的可能直接就是对象。正确写法：
//   const stored = await Host.secureStore.get('auth');
//   const data = (typeof stored === 'string') ? JSON.parse(stored) : stored;
// 只写 JSON.parse(stored) 的话，对象会被 String() 成 "[object Object]"
// 再抛语法错误 —— init 静默 return false，登录后家庭/设备全空。

// 加密
Host.crypto.sha1Hex(s) / sha256Hex(s) / sha256Base64(s)
Host.crypto.sha1BytesBase64(b64) / sha256BytesBase64(b64)   // 字节级，见下
Host.crypto.base64ToHex(b64) / hexToBase64(hex)
Host.crypto.hmacSha1(key, s)
Host.crypto.randomBytes(n)      → base64                              // 需 crypto

// 日志
Host.log.info(tag, msg) / Host.log.error(tag, msg)                    // 需 log

// 宿主缓存
Host.getDevice(did) → Device | null       // 不需要额外权限

// 原始 socket（见 §7.4）
Host.udp.*   // 需 lan
Host.tcp.*   // 需 lan
Host.tls.*   // 需 mqtt
```

以上全部返回 Promise，都要 `await`。`http` / `httpForm` 的返回值有四个字段：
`status`（HTTP 状态码）、`body`（响应体字符串）、`headers`（响应头，**键名已统一小写**）、
`cookies`（系统解析好的 Cookie 串）。宿主**不**替你做 HTTP 状态判断，
因为不同平台的错误语义差别很大（有的平台把业务错误藏在 200 的 body 里）。

🔴 **`cookies` 和 `headers` 不是可有可无的**。很多平台的登录流程靠 Cookie 串联
——先请求 A 拿到 Cookie，请求 B 必须带上它。米家就是典型：

```
GET /pass/serviceLogin   → 响应带 Set-Cookie: serviceToken=...
GET /longPolling/loginUrl → 必须带上 serviceToken，否则服务端返回**空响应**
```

少了这一步，服务端不会报错，只是给一个不含 `loginUrl` / `qr` / `lp` 的响应，
表现成「二维码出不来」——**完全看不出是 Cookie 的问题**。

取 Cookie 请**优先用 `res.cookies`**（SDK 直接解析好的结果），`headers['set-cookie']`
只作兜底：`set-cookie` 可能是数组、可能被系统合并、老版本宿主还可能不返回 `headers`。

```js
function absorbCookies(res) {
  let raw = res.cookies ? String(res.cookies) : '';
  if (!raw && res.headers) raw = String(res.headers['set-cookie'] || '');
  if (!raw) return;
  // 一个响应可能带多个 Set-Cookie，用「逗号后紧跟 name=」切分
  const parts = raw.split(/,(?=\s*[^=;]+=)/);
  for (const part of parts) {
    const pair = part.split(';')[0].trim();
    const eq = pair.indexOf('=');
    if (eq <= 0) continue;
    // 同名覆盖，保留其余……
  }
}
```

**关于 `Host.http`**：这是你发网络请求的**唯一**方式。沙箱里的 `fetch`/`XHR` 会被 CORS 挡住。
好处是它顺带统一了 UA、超时和日志，排查问题时宿主能把完整请求链导出给你。

### 7.1 ⚠️ 没有 `Host.crypto.rc4`

早期草案里写过 `Host.crypto.rc4(keyBase64, dataBase64)`，**这个能力不存在，不要用**。

原因：鸿蒙的系统加密库（`@ohos.security.cryptoFramework`）只提供 AES / 3DES / SM4 /
ChaCha20 这类标准算法，**不含 RC4**。宿主没法凭空多出一个系统不支持的算法。

需要 RC4 的话（比如米家的签名流程），请**在插件自己的 JS 里实现**，
标准实现只有十来行：

```js
function rc4(keyBytes, dataBytes) {
  const S = new Uint8Array(256);
  for (let i = 0; i < 256; i++) S[i] = i;
  let j = 0;
  for (let i = 0; i < 256; i++) {
    j = (j + S[i] + keyBytes[i % keyBytes.length]) & 0xff;
    const t = S[i]; S[i] = S[j]; S[j] = t;
  }
  const out = new Uint8Array(dataBytes.length);
  let i = 0; j = 0;
  for (let k = 0; k < dataBytes.length; k++) {
    i = (i + 1) & 0xff;
    j = (j + S[i]) & 0xff;
    const t = S[i]; S[i] = S[j]; S[j] = t;
    out[k] = dataBytes[k] ^ S[(S[i] + S[j]) & 0xff];
  }
  return out;
}
```

放在插件里其实更合适：米家等平台的 RC4 常有变体（丢弃前 N 字节、密钥派生方式不同），
放在宿主反而没法按各家需求定制。

### 7.1.1 字节级摘要与编解码（`BytesBase64` / `base64ToHex`）

RC4 那个例子暴露了一个通用陷阱：米家的签名链路里，**输入往往已经是解码好的原始字节**，
而不是 UTF-8 文本。`ssecurity`、`nonce` 都是 Base64 串，要先把它们解码，
拼接**字节**，再摘要。

如果用 `sha256Base64(s)` 直接拼字符串，你算出来的是「Base64 文本的摘要」，
和协议要求完全不同 —— 服务端只会回一个语焉不详的 401，很难排查。

所以提供了四个方法：

| 方法 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `sha1BytesBase64(b64)` | Base64 二进制 | Base64 二进制 | 字节级 SHA-1 |
| `sha256BytesBase64(b64)` | Base64 二进制 | Base64 二进制 | 字节级 SHA-256 |
| `base64ToHex(b64)` | Base64 | hex 小写 | 纯编码转换，**不需要 crypto 权限** |
| `hexToBase64(hex)` | hex | Base64 | 同上 |

对照一下米家的 `signedNonce`：

```js
// ❌ 错：把 Base64 文本当字节摘要，结果对不上
const signed = await Host.crypto.sha256Base64(ssecurity + nonce);

// ✅ 对：先各自解码成字节，拼接后再摘要
const a = await Host.crypto.base64ToHex(ssecurity);
const b = await Host.crypto.base64ToHex(nonce);
const signed = await Host.crypto.sha256BytesBase64(
  await Host.crypto.hexToBase64(a + b)
);
```

最后那句看着绕，但它是「把两段字节拼起来」最省事的写法 ——
`hexToBase64` 把拼接后的 hex 重新变成二进制喂给摘要方法。
你也可以自己在 JS 里用 `Uint8Array` 拼接，效果一样。

### 7.2 桥的形态说明

你看到的 `Host.secureStore.get(...)` 是**嵌套对象**，但底层注入到 ArkWeb 的是
扁平方法（`Host.secureStore_get`）。这层缝合由宿主在 bootstrap 脚本里完成，
对你无感。你只需要按上面写的形态调用。

另外，桥调用失败时**会抛异常**（而不是返回 `{ok:false}`），所以直接 `try/catch`
或者让它冒泡到 `Plugin.register` 的各个钩子里即可。最常见失败原因是权限没声明。

### 7.3 原始 socket：为什么必须由宿主提供

沙箱里**没有任何原始 socket API**：

- `fetch` / `XHR` 只能走 HTTP，还被 CORS 挡着（所以另开了 `Host.http`）；
- 没有 `dgram` / `net` / `tls` 这类 Node 风格模块；
- WebSocket 是唯一的长连接手段，但**说不了 MQTT、miio 这些私有协议**。

所以凡是「发原始字节 / 收原始字节」的需求，都得由宿主代发。这就是 §7.4 那三组 API。

### 7.4 `Host.udp` / `Host.tcp` / `Host.tls`

**UDP**（局域网设备发现与明文控制，如 miio 的 54321）—— 需 `lan`：

```ts
const h = await Host.udp.open({ localAddress: '0.0.0.0', localPort: 0 });

// 注册回调：收到报文时被调用，参数是 [dataBase64, host, port]
// ⚠️ 注册必须在 send 之前，否则第一包回得快就会丢
await Host.udp.onMessage(h, (dataB64, host, port) => { /* ... */ });

await Host.udp.send(h, '192.168.1.23', 54321, someBase64);
await Host.udp.close(h);
```

**TCP**（局域网内需要连接语义的设备）—— 需 `lan`：

```ts
const h = await Host.tcp.open({ host: '192.168.1.23', port: 9999, timeout: 10000 });
await Host.tcp.onMessage(h, (dataB64) => { /* ... */ });
await Host.tcp.onClose(h, () => { /* 断线了，在这里做重连 */ });
await Host.tcp.send(h, someBase64);
await Host.tcp.close(h);
```

**TLS**（到公网 broker 的加密长连接）—— 需 `mqtt`：

```ts
const h = await Host.tls.open({
  host: 'cn-ha.mqtt.io.example.com',
  port: 8883,
  clientCert: pemCert,     // 双向认证的客户端证书（PEM）
  clientKey: pemKey,       // 对应私钥（PEM，PKCS#8）
  ca: '',                  // 留空 = 不校验服务端证书链
  timeout: 15000
});
await Host.tls.onMessage(h, (dataB64) => { /* MQTT 报文 */ });
await Host.tls.onClose(h, () => { /* 重连 —— 注意 MQTT 重连后必须重新订阅 */ });
```

#### 载荷一律 Base64

跨 JS 边界只能传字符串，而报文是任意二进制。用 Base64 而不是十六进制，
因为二进制协议里 hex 会让数据量白白翻倍：

```js
// 发：Uint8Array → base64
function toB64(bytes) {
  let s = '';
  for (const b of bytes) s += String.fromCharCode(b);
  return btoa(s);
}
// 收：base64 → Uint8Array
function fromB64(b64) {
  const s = atob(b64);
  const out = new Uint8Array(s.length);
  for (let i = 0; i < s.length; i++) out[i] = s.charCodeAt(i);
  return out;
}
```

#### 回调是怎么被调起来的

桥上的「回调」是**方向相反**的调用：宿主收到报文后，通过
`webController.runJavaScript` 往沙箱里推。因为函数没法穿过 JSON 序列化的边界，
宿主记的是**回调名**，沙箱侧由 bootstrap 维护注册表（`cb_1` / `cb_2` …）。

对你是透明的，但有一点要注意：**回调注册表在页面重建后会清空**。
宿主在 Web 重建时会重新注入 bootstrap，届时旧的注册名就失效了 ——
所以插件在 `init()` 里重新注册一遍回调是必要的（别只在模块顶层注册一次）。

#### 三个必须知道的边界

1. **TCP 是流，不是消息**。`onMessage` 的每一次回调**不代表一个完整报文** ——
   TCP 会任意切包、也会粘包。协议解析必须自己攒缓冲区（见 §11 的 MQTT 例子）。
   UDP 相反，一次回调就是完整一包。
2. **连接归插件所有，但要显式关**。插件被停用/卸载时宿主会替你收掉全部 socket，
   但正常使用中请自己 `close` —— socket 是稀缺资源，开着不放会占端口。
3. **`tls` 的 `ca` 留空意味着不校验服务端身份**。这对使用私有 CA 的 broker 是必需的，
   但确实是安全折衷。需要严格校验时把 CA 的 PEM 传进来。

### 7.5 ⚠️ 仍然没有 `Host.crypto.rc4`

见 §7.1 —— 系统加密库不含 RC4，需要的话在插件自己的 JS 里实现。

## 8. 版本协商

宿主加载插件前会检查两件事，任一不满足就拒绝加载并给出可读提示：

1. `plugin.schemaVersion` ≤ 宿主支持的最大 schema 版本（当前 **1**）
2. `plugin.hostMinVersion` ≤ 宿主当前版本

宿主升级导致旧插件不兼容时，插件会被标记为「需要更新」而不是直接崩溃 ——
用户的设备列表仍然从缓存里读，不会白屏。

## 9. L0：声明式插件（无代码）

如果你的平台就是「REST + 固定签名算法 + JSON」，可以不写一行 JS：
`runtime: "declarative"`，把端点写进 `plugin.json` 的 `flows` 里，宿主用内置引擎解释执行。

```jsonc
{
  "runtime": "declarative",
  "auth": { "type": "bearer", "tokenFrom": "secureStore:token" },
  "signer": "hmac-sha256",          // 宿主内置：none | hmac-sha1 | hmac-sha256 | md5-sorted
  "flows": {
    "getHomes":  { "method": "GET",  "url": "{base}/v1/homes", "resultPath": "data.homes" },
    "getDevices":{ "method": "GET",  "url": "{base}/v1/devices",
                   "mapping": { "did": "id", "name": "nickname", "model": "product_id" } }
  }
}
```

**限制**：做不到有状态登录（只能用 `bearer` / `basic` / 静态 header）、做不到二进制协议、
做不到 MQTT。遇到这些就升级到 `runtime: "js"`。

## 10. 发布

### 10.1 用 GitHub Release（推荐）

1. 打 tag：`v1.0.0`（必须与 `plugin.json` 的 `version` 一致，**不带 `v` 也行，宿主会自动去掉**）
2. 把 `my-platform-1.0.0.zip` 作为 release asset 上传
3. 可选：同名 `.sha256` 文件，宿主会校验

用户在应用里粘贴 `https://github.com/you/repo` 即可安装，
宿主会去读 `releases/latest` 并匹配 `assetPattern`。

⚠️ GitHub 未认证 API 限流 **60 次/小时/IP**。用户装不上时，让他改用直链。

### 10.2 直链

直接给 zip 的 HTTPS 直链也行（自建服务器、对象存储）。同样的 zip 格式。

### 10.3 签名（⏳ 尚未实现）

下面描述的是**规划中的机制，当前宿主还没做任何签名校验**：

- 规划：zip 里放 `plugin.sig`（对 `plugin.json` + `main.js` 的 Ed25519 签名），
  manifest 里填 `publicKey`；宿主默认只自动信任内置白名单仓库的插件，
  其余弹「未签名插件」警告，需用户手动确认。

现实情况与使用建议：

- 现在**任何**来源的插件装上后都会走同一套「展示权限 → 用户确认 → 启用」流程，
  没有额外的签名门槛；
- 因此**只装你信得过的来源**。权限弹窗里那些条目就是真实的边界，
  比如一个只声明 `network` 的插件碰不到你的本地存储；
- 别在插件里填 `publicKey`，宿主目前会忽略它 —— 填了不会报错，但也不会更安全。

## 11. 从 HA 集成移植的操作步骤

以把一个 HA 集成（`custom_components/foo/`）搬过来为例：

1. **看 `config_flow.py`** → 决定 `login.type`：
   - 有 `async_step_auth` + 二维码 → `qr`
   - 有 OAuth2 `authorize_url` → `web`
   - 只有 `async_step_user` 填 host/token → `form`
2. **看 `__init__.py` 里的 `async_setup_entry`** → 对应你的 `init()`，
   把 `hass.data[DOMAIN][entry.entry_id]` 里的那个 client 对象改写成 JS 闭包。
3. **看 `api.py` / `client.py`** → 每个 `async def get_xxx` 翻译成 `Host.http(...)`，
   注意 HA 里常用的 `aiohttp` 默认行为（自动解 gzip、自动跟重定向）在 `Host.http` 上也是默认行为。
4. **看 `entity.py`** → 决定 §6.2 走哪条路：翻译成 MIoT 还是返回 `null`。
   HA 的 `supported_features` / `device_class` 是最有用的映射线索。
5. **看 `const.py` 的 `DOMAIN`** → 作为你的 `plugin.id` 前缀，避免撞车。
6. **删掉**：`manifest.json`（换成 `plugin.json`）、`translations/`、`requirements`（依赖得自己用 JS 实现）。

**最容易踩的坑**：HA 集成普遍假设「有个 Python 生态」（`paho-mqtt`、`cryptography`、各种 SDK）。
JS 里没有现成替代时，先看 `Host.crypto` 覆盖了没有（目前有 sha1/sha256/hmac-sha1/随机数，
**没有 rc4 和对称加密**，见 §7.1）；再没有就只能自己实现。
**MQTT 目前没有宿主支持**（见 §7.3），需要长连接的集成只能改用轮询。

## 12. 最小示例：一个 `form` 登录的云插件

这个示例的**完整可运行版本就在本仓库里**：

```
plugins/sample-plugin/
├── plugin.json      清单
└── main.js          插件本体
```

应用内点「安装内置示例」即可装上（不需要网络，也不需要真机打包），
它是验证宿主链路是否正常的最快手段。下面摘录关键部分说明写法，
**以仓库里的文件为准**（文档和代码不一致时，是文档过期了）。

```js
// main.js 摘要
let auth = null;

Plugin.register({
  async init() {
    const stored = await Host.secureStore.get('auth');
    if (!stored) return false;
    // ⚠️ 桥的拆包层会把形似 JSON 的字符串 parse 成对象（见 §7 secureStore 陷阱），
    // 两种形状都要接得住
    auth = (typeof stored === 'string') ? JSON.parse(stored) : stored;
    return true;
  },

  async loginBegin() {
    const id = 's' + Date.now();
    return {
      sessionId: id,
      view: {
        type: 'form',
        fields: [
          { key: 'host',  label: '服务器地址', type: 'text',     placeholder: 'http://192.168.1.10:8123' },
          { key: 'token', label: '长期令牌',   type: 'password' }
        ],
        submitLabel: '连接'
      }
    };
  },

  async loginSubmit(_id, fields) {
    const res = await Host.http('GET', `${fields.host}/api/`, {
      'Authorization': `Bearer ${fields.token}`
    });
    if (res.status !== 200) {
      return { state: 'error', message: `连接失败（${res.status}）` };
    }
    auth = { host: fields.host, token: fields.token };
    await Host.secureStore.set('auth', JSON.stringify(auth));
    return { state: 'success' };
  },

  async getHomes() {
    return [{ id: 'default', name: '全部设备', roomIds: [] }];
  },

  async getDevices() {
    const res = await Host.http('GET', `${auth.host}/api/states`, {
      'Authorization': `Bearer ${auth.token}`
    });
    const states = JSON.parse(res.body);
    const out = {};
    for (const s of states) {
      const did = s.entity_id;
      out[did] = {
        did, name: s.attributes.friendly_name ?? did,
        model: did.split('.')[0], urn: '', roomId: '', homeId: 'default',
        online: s.state !== 'unavailable',
        token: '', localIp: '', parentDid: '', subDevices: {}
      };
    }
    return out;
  },

  async getSpecForDevice() { return null; },      // 降级为简化卡片
  async createTransports() { return []; },        // 只读，不控制

  async dispose() { auth = null; }
});
```

配套的 `plugin.json` 把 `capabilities` 里除 `homes` / `devices` 之外全设 `false`，
`login.type` 设 `form`，`permissions` 填 `["network", "secureStore", "log"]` —— 一个只读看板插件就完成了。

**实际文件**在 `plugins/sample-plugin/`，比上面摘要多了几处
容错处理（地址没写协议时自动补 `http://`、去掉结尾斜杠、拿不到凭据时返回空列表
而不是抛错），可以直接对照阅读。

### 12.1 第二个示例：局域网探测（`Host.udp` 的用法）

仓库里还有一份样例 `plugins/sample-lan-plugin/`，
演示 §7.4 的原始 socket 桥：对用户填的网段发 UDP 探测，把有应答的主机当作设备列出。

它刻意**不实现任何厂商协议**（探测包里就是一段明文），目的是让
「打开 UDP → 注册回调 → 发包 → 收包 → 转成设备」这条链路能被肉眼验证。
挑几个要点：

```js
// 1. 载荷是 Base64 —— 跨 JS 边界只能传字符串
function b64ToBytes(b64) {
  const s = atob(b64);
  const out = new Uint8Array(s.length);
  for (let i = 0; i < s.length; i++) out[i] = s.charCodeAt(i);
  return out;
}

// 2. 注册必须在发包之前，否则回得快的第一包会丢
const handle = await Host.udp.open({ localAddress: '0.0.0.0', localPort: 0 });
await Host.udp.onMessage(handle, function (dataB64, host, port) { /* ... */ });
await Host.udp.send(handle, '192.168.1.23', 54321, utf8ToB64(probe));

// 3. 用完一定要关：socket 是稀缺资源，开着不放会占住本地端口
await Host.udp.close(handle);
```

⚠️ 别用 `TextEncoder` 处理收发到的字节：UDP 报文是**任意二进制**，
走 UTF-8 编解码会在非 ASCII 字节上直接损坏数据。只用 `atob` / `btoa`。

## 13. 自己验证插件

### 13.1 先在电脑上跑：`scripts/simulate_plugin_load.js`

插件的加载失败在真机上只会显示一句话，具体原因藏在日志里。所以**不要一上来就装机试**——
先用模拟器在电脑上把插件的加载过程跑一遍：

```bash
node scripts/simulate_plugin_load.js <插件目录> [入口文件名]
# 例：node scripts/simulate_plugin_load.js plugins/mijia-cloud
```

它在 Node 的 `vm` 里**逐字复现宿主的 `wrapSource`**（同一段 IIFE 结构、同样的
`try/catch` + `__reportFatal__`），把 `Plugin` / `Host` 换成可观测替身，然后分步打印：

1. 注入源码时有没有直接抛错（语法错误会在这里现形）
2. 插件有没有成功 `Plugin.register`（等价于宿主的 probe）
3. 注册出来的钩子清单
4. 逐个调用 `init` / `getHomes` / `getDevices` / `createTransports` / …，把每个的返回或异常打出来
5. 插件调了哪些宿主桥方法（以及调用的先后顺序）
6. 宿主日志里会看到的那句 probe 字符串

它**不发起真实网络请求**（`http` / `httpForm` 是替身，调用即抛），所以能安全地反复跑。
只做计算的部分（签名、编解码、加解密）则可以放心验证到具体数值。

**想看登录链路的话，加 `--stub-net`**：

```bash
node scripts/simulate_plugin_load.js plugins/mijia-cloud --stub-net
```

它会把 `Host.http` 换成返回固定假票据的替身，并多跑一步 `loginBegin()`，
**逐条复现宿主的判定**（`sessionId` 为空？`view` 缺失？`view.type` 是否三选一？
`imageUrl` / `pollInterval` 给了没？）—— 最后告诉你宿主会把面板渲染成什么。

之所以需要这个开关：`loginBegin` 这类钩子**第一件事就是发网络请求**，
没有桩的话必然在第一个请求上抛错，它本该返回的视图就永远看不到。
注意它给的是「合法响应」，用途是**照相机而不是测试** —— 分支逻辑还是要靠真机或单元测试覆盖。

这套流程能提前抓到绝大多数「装进去就不动」的问题，尤其是：

- 源码里写了 `import` / `export` —— **会直接抛语法错误**（见 §1.1，插件只能是单文件脚本）
- 加载期的顶层代码抛异常（模块级变量初始化时踩空、读了不存在的 `Host.xxx`）
- 忘了调 `Plugin.register`，或传给它的不是对象
- 某个钩子返回了不可序列化的东西

### 13.1.0 先跑这个：`scripts/check_bootstrap_template.js`

**改完 `PluginSandbox.ets` 先跑它。** 原因是那个文件里有好几个

### 13.1.1 验证宿主桥本身：`scripts/verify_bootstrap_stitch.js`

上面那个模拟器**直接给沙箱注入一个 `Host` 替身**，跳过了宿主的
`BOOTSTRAP_SCRIPT` 缝合步骤 —— 所以它测不出「桥根本没缝出来」这类故障。

```bash
node scripts/verify_bootstrap_stitch.js
```

它从 `PluginSandbox.ets` 里**把真实的 `BOOTSTRAP_SCRIPT` 抠出来**，
在 Node `vm` 里用四种情形跑一遍：

| 情形 | 期望 |
| --- | --- |
| `Host` 是**函数**（ArkWeb JSProxy 的真实形态） | 缝合成功，`Host.http` / `Host.secureStore.get` 可调用，且调用**真的打到了原始桥** |
| `Host` 是普通对象（旧内核 / 测试替身） | 缝合成功 |
| `Host` 不存在（桥没注册） | 回 `fatal:原生桥未注册…`，**不能静默当成功** |
| 信封拆解 | 空 `data` 归一成 `null`；`ok:false` 的 `error` 要**抛**到插件侧 |

改动 `BOOTSTRAP_SCRIPT` 或桥的方法清单后应该跑一次。

### 13.1.2 验证调用握手：`scripts/verify_invoke_handshake.js`

```bash
node scripts/verify_invoke_handshake.js
```

`verify_bootstrap_stitch.js` 只覆盖**插件侧**那一半（派发与回推）。
宿主侧那一半（挂等待槽 → 派发 → 校验 ack → 等回推 → 拆信封）是纯 ArkTS，
跑不了 Node —— 但它的**时序**恰恰最容易错。这个脚本把宿主那段逻辑
照抄一份，接上真实的 `BOOTSTRAP_SCRIPT`，跨端跑一遍：

| 情形 | 期望 |
| --- | --- |
| 基本往返（插件方法是 `async`） | 拿到返回值，且等待槽清空 |
| 插件方法**同步**返回 | 也拿得到（证明「先挂槽再派发」的顺序是对的） |
| 插件抛错 | 错误文案透传到宿主，槽清空 |
| `__miha_invoke__` 不存在（页面被重建） | 给「环境正在重建」而不是干等超时，且不残留槽 |
| 插件方法永不结算 | 超时后**抛错**且**槽被清掉**（清槽必须写在 `finally` 里） |
| 换插件作废旧调用 | 立即抛「已切换」；旧插件的迟到结果被丢弃 |
| 并发调用 | 乱序完成仍各自拿到自己的结果（`callId` 不串） |
| 回推通道失效 | 结果经**孤儿表**救回，而不是白等 60 秒 |

⚠️ 这个脚本里宿主的逻辑是**照抄**的，不是导入的 —— 改了
`PluginSandbox.invoke` / `onInvokeSettle` / `onInvokeCancelAll` /
`pickupOrphan` 之后，记得把对应片段同步过去，否则它验的是旧逻辑。
两边都抄意味着它只能证明「宿主与插件的约定自洽」，
**不能**证明「ArkWeb 真的会这样行为」—— 那只能靠真机。

### 13.3 按症状定位

| 症状 | 先查这里 |
| --- | --- |
| 卡片上**没有**「登录」按钮 | `plugin.json` 的 `login.type` 写了没 / 写对没；卡片处于「不兼容」状态时也不给 |
| 点「登录」提示「插件未能加载：XXX」 | **冒号后面的 XXX 就是确切原因**，照它查；没带冒号说明是插件连不上沙箱 |
| 提示「插件运行环境未就绪」 | 页面里的运行环境还没准备好。宿主会等 3 秒，超时说明 ArkWeb 没起来（真问题，需要查页面） |
| 提示「插件加载出错：…」 | 插件加载期抛的异常，引号里是原始 message |
| 提示「插件没有调用 Plugin.register」 | 插件跑到最后没注册自己，或注册时抛错被吞了 |
| 提示「读取插件入口失败」 | `plugin.json` 的 `entry` 指向的文件不存在 / 是空的 |
| 提示「插件尚未启用」 | 卡片还是「待启用」状态，需要先确认权限 |
| 登录面板一直转圈 | `loginBegin` 没返回 `sessionId`；`qr` 视图记得给 `pollInterval` |
| 面板显示「正在准备登录…」+ 转圈 | **正常**，宿主在等 `loginBegin` 返回。若一直停在这里，多半是 `loginBegin` 里的网络请求卡住了（宿主上限 60s，桥的单个请求上限 15s） |
| 面板显示「等待操作…」且下方空白 | 宿主拿到的视图里既没二维码、也没授权页 URL、也没有表单字段。检查 `view.type` 是否写成了协议外的值（只认 `qr` / `web` / `form`） |
| 面板显示「轮询失败」 | 宿主连续 3 次调 `loginPoll` 都抛错（一次网络抖动会被容忍） |
| 二维码不显示 | `imageUrl` 给的地址宿主下不下来；沙箱里不能 `fetch` 图片 |
| `Host.udp` 是 undefined | `permissions` 里没声明 `lan` |
| 收发报文内容不对 | 大概率是 base64 ↔ Uint8Array 转换写错了（§7.4） |
| `Host.tls.open` 报错 | 常见是 `isBidirectionalAuthentication` 开了却没配 `clientCert` / `clientKey` |
| 日志出现 `未成功注册: "yes"`（**值带引号**） | **不是插件的问题**，是宿主解析 `runJavaScript` 返回值的容错 bug（旧版本）。返回值被 ArkWeb 包了一层引号，和裸 `yes` 比不出来。新版本已剥壳；若还遇到，说明 `PluginSandbox.normalizeJsResult` 又有回归 |
| 插件注册成功，但所有方法调用都抛「执行失败」 | 同上 —— `unwrapResult` 拿到的 JSON 被包了一层引号，`JSON.parse` 出来是字符串而非对象，`parsed.ok` 恒为 `undefined`。已修复 |
| 日志出现 `bootstrap 失败: fatal:原生桥未注册` | 两种可能：① 桥还没走到第 2 轮加载（正常时序里**不该**出现这条，出现即说明时序异常）；② `registerJavaScriptProxy` 真的失败了。先搜日志里有没有 **`[PluginSandbox] 宿主桥就绪`**。本地可用 `node scripts/verify_bootstrap_stitch.js` 排除缝合逻辑本身的问题 |
| 日志出现 `native proxy object not found, name:Host` | 沙箱的 Web 被 ArkUI 重建了（弹窗、父组件重渲染都会触发），旧代理随之失效。见 §4.1.3 |
| 报 `cannot read property ok of null` | 多半是上面那条的**后果** —— 调用进行到一半桥没了，返回值跨过来成了 `null`。宿主已加防护（回一句可读的错误而不是崩），但根因是重建，见 §4.1.3 |
| 日志出现 `Host 未就绪，跳过重复注册` / `原生代理已注册过` | **正常**。说明组件重建后复用了同一个 controller，宿主正确地跳过了重复注册 |
| 日志出现 `bootstrap 结果异常，拒绝继续` | bootstrap 脚本回传了非 `ok`/`already` 的内容，说明脚本没真正执行（或被 CSP 拦下）。这是**保护性失败**，避免后面撞在「Host 未定义」上 |
| 报「插件方法 X 返回的不是有效信封: null」 | 调用脚本是 **async IIFE**，而 `runJavaScript` 不等 Promise 结算（SDK 原文：*"has no return value, null will be returned"*），于是每次都拿到字符串 `null`。见 §4.1.4。新版本改用「同步返回 + 回调回推」，不该再出现；若复现，检查 `buildInvokeScript` 是否被改回了 async 形态 |
| 报「插件运行环境正在重建，请重试」 | 沙箱页面刚被 ArkUI 重建，宿主正在自愈。**重试即可**（通常几百毫秒内恢复）。见 §4.1.8 |
| 报「插件方法 X 未受理（脚本返回 …）」 | 派发脚本没能跑起来 —— 插件 `entry` 文件有语法错误，或沙箱状态异常。对比 `node scripts/verify_bootstrap_stitch.js`（§13.1.1）排除派发逻辑 |
| 运行一阵子后突然报 `FindObject Unknown object` / `host does not have the interface method` | 代理对象被 GC 了（宿主早期忘记持有强引用）。**不是插件的问题**，见 §4.1.5。宿主已修（`proxyObject` 字段保活 + 孤儿表兜底） |
| 调用失败但**恰好拿回了正确结果** | 走了孤儿表兜底路径（回推断了、宿主主动捞回）。日志里会有「结果经孤儿表捞回」。功能正常，但说明桥曾经失效过一次，值得看一眼 `native proxy object not found` 的出现频率 |
| 插件被重新 `register` 了一次 | 沙箱自愈（§4.1.8）。若 `init()` 有副作用，把它写成幂等的 |
| 日志出现 `FIX THIS APPLICATION ERROR: ... 'pageInfos' has changed during render!` | **不要只查调用位置** —— 去该状态的 `@Watch` 链路上找**同步重入**。本工程真凶是 `consumePendingDeviceDetail` 里「先 `AppStorage.setOrCreate` 清标记、后推路由」，被 `@StorageProp + @Watch` 同步重入了一轮，第二次执行推了路由。⚠️ 外层包 `setTimeout` **无效**（重入在函数内部）。见 §4.1.6 |
| 日志出现 `web controller is nullptr` | ArkWeb 首次构建 `Web` 组件时的内部噪音，**通常无害**。判定看三行是否配对：只要后续有 `CreateNWeb NWebId: N, size 1*1` 与 `NWeb size change from 0*0 to 1*1`，沙箱就是好的。见 §4.1.8 |
| 日志出现 `RegisterClientDeathObserver failed` / `Found no matching cache` | **系统噪音**，与本工程无关，别顺着它查 |

日志里搜 `[plugin:<你的插件id>]` 可以看到 `Host.log` 的输出，
`[PluginSandbox]` 前缀的是宿主侧的加载过程（注册失败、bootstrap 失败都会打在这里）。

> **为什么提示语现在带原因了**：这些失败原先不管哪一类都只说「插件未能加载，请先启用它」，
> 而用户往往已经启用过了——那句话既解释不了问题，也让人无从下手。现在
> `PluginSandbox` 会记录具体原因，`PluginManager.connect` 取走后拼进提示里
> （`consumeLoadError()` / `consumeConnectError()`），界面直接展示。
